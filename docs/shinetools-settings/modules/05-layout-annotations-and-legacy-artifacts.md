## 模块结论

三个画板不仅包含设置项树，还混有标题、版面标记、空白根节点和产品评审批注。它们是重要的来源证据，但不是可直接执行的设置定义。

本模块得出四个结论：

1. 每个画板都有 6 个脑图根节点和 1 个独立文字对象；7 类顶层对象已经全部归档。
2. 三个画板共享旧根节点 ID，MIN-XH 和研发端中仍保留独立的 `MOD - XH` 标题，说明三个画板存在明显的复制或共用模板痕迹。
3. `新版，只看这个` 是独立的 `text_shape`，不是脑图节点。它在版面上划分了新版重点区和旧版参考区，但生命周期含义仍需产品负责人确认。
4. 设置名称中混入了大量“删除、确认、建议、不显示、开关按钮”等说明。进入正式 SSOT 前，必须把显示名、交互类型、适用性、生命周期和评审状态拆成不同字段。

| 属性 | 结论 |
|---|---|
| 内容性质 | 来源治理与质量归档，不是功能模块 |
| 当前用途 | 解释版面结构、生命周期线索和评审批注 |
| 不建议用途 | 不应把标题、批注或删除建议直接生成设置项 |
| 来源稳定性 | 三份画板的旧版视觉对象 ID 和位置高度一致 |
| 处理状态 | 已完成来源归类；产品决策仍保留为待确认 |

## 分析边界

本文处理以下内容：

- 独立标题 `MOD - XH`
- 没有子项的第一个 `直连模式`
- 独立文字对象 `新版，只看这个`
- 设置名称后通过 `/`、括号或换行附加的评审说明
- 删除线、重复项、重命名建议、机型可见性和交互提示

本文不重新分析四棵功能树：

- 新版 `Quick Site Setup` 由 [M01](./01-quick-site-setup.md) 处理。
- 新版 `直连设置（Shinetools 平台）` 由 [M02](./02-direct-settings-platform.md) 处理。
- 旧版 `quick Setting` 由 [M03](./03-reference-quick-setting.md) 处理。
- 旧版完整 `直连模式` 由 [M04](./04-reference-direct-mode.md) 处理。

## 非功能对象清单

三个 RAW JSON 的顶层对象结构相同：

| 对象 | 原始 ID | 类型 | 子节点 | 三视图情况 | 本专题归属 |
|---|---|---|---:|---|---|
| `MOD - XH` | `z1:610` | `mind_map` | 0 | 三份都存在 | M05：复制遗留标题 |
| 第一个 `直连模式` | `z1:165` | `mind_map` | 0 | 三份都存在 | M05：空白视觉标签 |
| `新版，只看这个` | `a5:1` | `text_shape` | 不适用 | 三份都存在 | M05：版面与生命周期标记 |

三个对象都不应进入设置项层级：

- `MOD - XH` 没有子项，且出现在并非 MOD-XH 命名的另外两份画板中。
- 第一个 `直连模式` 没有子项；同一画板内另有一棵 238 节点的完整同名树。
- `新版，只看这个` 不属于思维导图，不能通过 `parent_id` 成为功能树的父节点。

生成大纲中的 `新版（重点）` 和 `其他画板内容（参考）` 是导出脚本依据位置生成的阅读分组，不是 RAW JSON 中真实存在的标题节点。

## 复制与旧版残留证据

### 共享 ID

以下对象在三个画板中保持相同 ID：

| ID | 内容 | 位置关系 |
|---|---|---|
| `z1:610` | `MOD - XH` | 旧版区域上方 |
| `z1:165` | 空白 `直连模式` | 旧版区域上方 |
| `z1:170` | 完整 `quick Setting` | 旧版参考区 |
| `z1:254` | 完整 `直连模式` | 旧版参考区 |
| `a5:1` | `新版，只看这个` | 新旧区域之间 |
| `z5:150` | 新版直连设置 | 新版重点区 |

`Quick Site Setup` 只有 MOD-XH 使用 `z22:2`，MIN-XH 和研发端使用 `z5:142`；这与 MOD-XH 在该模块增加寄存器提示和 SOC 细分的事实一致。

### 可支持的判断

相同 ID、相同旧版子树和相同标记坐标共同构成强证据，说明三份画板来自同一模板、复制版本或共享快照。

### 不能由此直接证明的事项

- 不能证明三个视图已由各自负责人独立评审。
- 不能证明市场端与研发端内容一致就代表研发确认。
- 不能证明旧版树已经在正式产品中下线。
- 不能把 `MOD - XH` 当作 MIN-XH 或研发端的真实机型标签。

## 新版标记的含义

`a5:1` 的原文是 `新版，只看这个`，三个画板的位置均为 `y = 2238.1` 左右。旧版四个根节点位于它上方，新版两个功能根节点位于它下方。

| 区域 | 根节点 | 当前处理 |
|---|---|---|
| 标记上方 | `MOD - XH`、空白 `直连模式`、`quick Setting`、完整 `直连模式` | 视觉残留或历史参考 |
| 标记本身 | `新版，只看这个` | 生命周期线索，不是功能节点 |
| 标记下方 | `Quick Site Setup`、`直连设置（shinetools)平台` | 当前重点模块 |

因此，当前文档把下方两棵树作为活动分析入口，把上方两棵完整功能树作为迁移参考。不过“新版”是画板作者的版面指示，不等于正式的版本发布记录；M03 / M04 只能标为 `deprecated 候选`，不能在没有负责人确认时直接标为已废弃。

## 批注分类

| 分类 | 常见文本 | 应进入的结构化字段 | 当前证据强度 |
|---|---|---|---|
| 生命周期 | 删除、只保留一个、新版 | `lifecycle_status`、`successor_key` | 多为建议，需批准 |
| 评审决策 | 确认、讨论、建议、是否 | `decision_status`、`review_note` | 明确表示未决 |
| 重复与缺陷 | 重复、漏了、描述需修改 | `quality_issue` | 来源事实，修复方案待确认 |
| 适用性 | XH/HU 不显示、某机型没有、仅 Italy | `applicability`、`visibility_rule` | 需要能力或机型表验证 |
| UI 交互 | 开关按钮、二次确认 | `control_type`、`confirmation_required` | 设计提示，不是协议属性 |
| 重命名 | 改成 Retrofit/Parallel、简化为 General Setting | `display_name_candidate` | 候选名称，不应覆盖原文 |
| 协议映射 | `holdNN`、`inputN` | `register_hint` | 只保留提示，含义待协议确认 |

### 生命周期批注

例如 `PU Enable 删除`、`AC Voltage Protection 删除` 和 `Safety Parameters / 只保留一个`。这些文字证明画板作者提出了删除或合并方向，但没有给出替代键、确认人、批准日期或下线版本。

### 决策批注

例如 `Basic Parameters / 研发确认是否删除` 和 `Network Configuration and General Setting / 讨论是否简化为 General Setting`。它们必须进入问题或评审记录，不能成为用户可见标签的一部分。

### 适用性批注

例如 `Generator and Smart Load（XH/HU不显示）` 和 `Meter/CT setting(SPM/WIT/XH/HU,SPE 不显示)`。这类内容应转成机型能力矩阵，而不是只靠字符串判断页面是否显示。

### 交互批注

`开关按钮` 出现 147 行，是最常见的批注。它描述 UI 控件，不证明底层一定是布尔寄存器，也不证明开启和关闭使用同一写入协议。`二次确认` 则反映操作风险，仍需同时定义权限、警告文案、审计和失败回滚。

## 为什么不能直接作为设置项名称

如果把原始整行直接用作设置键，会产生以下问题：

1. 同一设置因为附加批注不同而生成多个键。
2. “删除”和“确认”会泄漏到最终用户界面。
3. 机型判断依赖自然语言，无法稳定执行。
4. UI 控件类型与寄存器类型混为一谈。
5. 产品建议可能被误执行为已经批准的变更。
6. 原文被清洗后又失去审计线索。

正确做法是保留不可变的 `source_text`，同时把可执行信息拆入经确认的结构字段。

## 建议的结构化模型

未来设置项 SSOT 至少需要以下字段组：

| 字段 | 作用 | 示例 |
|---|---|---|
| `setting_key` | 跨页面稳定标识 | `ems.parallel.enable` |
| `display_name` | 当前正式显示名 | `Parallel Setting` |
| `source_text` | 不修改的画板原文 | 完整含批注文本 |
| `source_ref` | 来源视图、节点 ID 和路径 | `market-mod-xh / z...` |
| `lifecycle_status` | 活动、参考、删除候选、已废弃 | `deprecated_candidate` |
| `decision_status` | 已确认、建议、待确认 | `needs_review` |
| `applicability` | 机型、地区、功率和版本范围 | `models: [XH, HU]` |
| `visibility_rule` | 页面显示条件 | `capability.parallel == true` |
| `control_type` | UI 控件类型 | `toggle` |
| `confirmation_required` | 是否需要确认交互 | `true` |
| `register_mapping` | 经协议确认的地址、类型和版本 | 当前为空 |
| `review_note` | 不直接执行的评审说明 | `XH/HU 机型都不展示` |
| `successor_key` | 删除或合并后的继任设置 | 待确认 |

建议状态枚举：

```yaml
lifecycle_status: active | reference | deprecated_candidate | deprecated
decision_status: confirmed | proposed | needs_review | rejected
```

`deprecated_candidate` 与 `deprecated` 必须分开：前者表示来源有删除意图，后者表示已经有负责人、替代关系和生效版本。

## 拆分示例

### 示例一：机型可见性与控件类型

来源文本：

```text
Parallel Setting / 开关按钮 / XH/HU 机型都不展示
```

候选拆分：

| 字段 | 值 |
|---|---|
| `display_name` | `Parallel Setting` |
| `control_type` | `toggle` |
| `visibility_rule` | `XH/HU hidden`，待能力表确认 |
| `decision_status` | `needs_review` |
| `source_text` | 保留完整原文 |

### 示例二：删除候选

来源文本：

```text
Inverter Protection 删除 / 需要研发对其相同设置项，只保留一个
```

候选拆分：

| 字段 | 值 |
|---|---|
| `display_name` | `Inverter Protection` |
| `lifecycle_status` | `deprecated_candidate` |
| `decision_status` | `needs_review` |
| `review_note` | 对齐相同设置项，只保留一个 |
| `successor_key` | 未知，禁止自动删除 |

### 示例三：字段遗漏

来源文本：

```text
Grid Connection Restriction / 漏了Vpv start（中文描述把PV和AC电压都叫并网电压，需修改描述）
```

候选拆分：

| 字段 | 值 |
|---|---|
| `display_name` | `Grid Connection Restriction` |
| `quality_issue` | 缺少 `Vpv start` |
| `review_note` | PV 与 AC 电压中文名称需区分 |
| `decision_status` | `needs_review` |

## 清理和迁移规则

1. RAW JSON 和生成大纲保持只读，不覆盖原文。
2. 标题、版面标记和空白根节点明确标为 `non_functional`，不生成设置键。
3. `/`、括号和换行后的内容先作为批注候选，不按标点机械删除。
4. `删除` 只转换为 `deprecated_candidate`，没有替代项和生效版本时禁止真正移除。
5. `确认`、`建议` 和 `讨论` 统一进入评审队列，不进入显示名。
6. `不显示` 和 `没有` 转成适用性候选，必须通过机型能力矩阵或实机验证。
7. `开关按钮` 只定义 UI 候选控件；协议读写类型必须独立确认。
8. 重复名称使用稳定 `setting_key` 区分，不能只按英文标签去重。
9. 当前区和参考区在未来 SSOT 中使用显式生命周期字段，不继续依赖画板坐标。
10. 每个已确认删除项记录确认人、日期、继任键、影响机型和生效版本。
